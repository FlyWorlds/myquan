# 行情、数据库与核对边界

本规则用于策略16当前报价驱动路径。它区分**数据来源、持久化确认、读取缓存和交易事件**，不是要求所有页面动作先写一次数据库。策略16B为条件选股展示；其他策略尚未统一迁移的路径不能默认套用本规则。

## 1. 分工

| 数据/动作 | 来源与优先级 | 写入要求 | 禁止事项 |
| --- | --- | --- | --- |
| 当前价、今日行情最高/最低、日内涨幅 | 新收到的可信行情及其真实源时间；当前策略16页面消费已确认报价缓存，原始行情接收独立运行 | 后台保存最新快照；不能等待分钟K线。实际执行仍以本次报价的入库确认为门槛 | 不拿数据库旧价格当新行情；不刷新源时间；不把日内最高等同持仓期间观测峰值 |
| 触价判断 | 比较实际收到的现价与已准备条件单，保留该事件价格/源时间/原始接收时间；不是查询历史最高来推断 | 当前真正执行仍在该报价确认入库后进行。内存发现触价不等于已买入 | 不因“曾越过买点”补记成交；不以数据库恢复读取、心跳或页面重绘触发交易 |
| 实际账户条件单 | 9:25后正式开盘、上一完整日线过滤、独立开盘复核；预备状态可在内存计算 | 实际账户的条件单和武装信息保存数据库，成功复核后才允许执行；开盘/参考条件变化要重新准备 | 不能把未落库的临时候选显示成跨设备已生效订单 |
| 独立策略账本候选 | 当前虚拟策略运行器的RAM候选，重启重新准备 | 候选不是实际Paper订单；真正虚拟成交、现金、数量、峰值/阶段由策略数据库确认 | 不能宣称RAM候选已经跨设备同步；不能与实际账户的每日两只/五槽混算 |
| 持仓、可用数量、现金、成本、槽位、日新增额度 | MySQL账户真源；页面读已确认版本缓存，成交前重新读取并做CAS | 买卖、现金、持仓、订单状态、成交和交割同一事务确认 | 不从实时价格推断“已经买入”；不从JSON恢复旧持仓；不在失败后本地假记成交 |
| 观测峰值、止盈阶段、T+1注记、卖出保护 | 当前已确认持仓状态加收到的可信报价，沿现有公式更新 | 关键状态变化立即持久化；必须带持仓周期与行情时序约束 | 不能从当日累计最高/最低补造过去交易；不能被纯估值写入节流丢失 |
| 已实现盈亏、全清后单笔收益 | 已确认买入和全部卖出腿的价格、数量、成本；优先读数据库流水/策略账本 | 随成交保存，修正必须有可追溯调整记录 | 不按最后一次卖价重算整笔；不按现价改写历史成交 |
| 浮盈、总权益、今日收益、仓位 | 同一账户版本的现金/持仓及带时间和版本的估值报价；实际账户与独立策略分开 | 页面只读计算/缓存；完整账户估值另有异步分钟采样，历史快照失败不修改交易状态 | 不把不同账户版本或不同报价时点的结果硬比较；缺价格时为未知，不当0盈利 |
| 日线、过滤参数、阈值、名称、板块标签 | 优先已有完整参考缓存，缺口后台补齐；当前日线/元数据并非全部入MySQL | 条件单保留参数和参考签名，日线缺口影响买入准备，不拖住行情接收 | 不每次渲染重拉全市场；不把日线补成1m路径；不宣称已经建成日线/全A分钟数据库 |
| 1分钟K线 | 独立历史/研究路径；先读已有覆盖，再按缺口采集 | 首屏渲染后低优先级研究备份，不作为实时交易依赖 | 不参与启动持仓恢复；不驱动策略16实时买卖、收益bootstrap或纠价 |

## 2. 三类价格必须分开

1. **观察价**：收到的行情价格，回答“该时点报了多少”。包括源时间、接收时间和可信度，不代表成交。
2. **估值价**：用于某份账户/策略收益的价格，必须说明报价时间和版本。它可能落后刚收到的观察价，不能隐瞒这个时间差。
3. **成交价**：经过条件、额度、现金、可用数量、T+1、时效和事务校验后确认的模拟成交价。按现有用户规则，买入挂单10.25、观察价10.80，仍按10.25模拟成交；二者分别记录，不声称券商真实成交。

`source time`、`received time`、`decision time`、数据库确认时间也分别记录。数据库读回和页面刷新不能重置前两者。

## 3. 优先读数据库，不代表重放数据库

- **启动持仓/现金**：读数据库权威账户，不从本地文件猜。
- **启动参考报价**：独立后台GET已存快照用于先展示已知数据。标记 `_reference_only=True`；不分发执行事件，不刷新有效信号时间，交易读取接口拒绝这种参考。
- **运行中的新报价**：继续优先接收；报价持久化ACK后的缓存才可供当前实际执行。源时间、原始接收时间仍要分别满足5秒上限。
- **共享数据库返回更新快照**：如果ACK返回的价格/源时刻不是本机这次实际收到的观察，只作参考，不能伪装成本机新触发。反过来，同一报价版本只有在确实再次收到该观察并完成幂等确认后，才可进入通常的时效/武装边界检查；单纯GET永远不具备这个资格。
- **页面收益/交割单/关闭交易**：读已确认账本及同版本读模型，不重新跑分钟历史。
- **读写竞争**：旧的慢GET不能覆盖较新ACK；错误响应不能回退JSON。参考读取错误与实时写入错误分别报告，不相互掩盖。

当前现价与收益页面主要读已确认缓存，不逐行同步查询数据库。本轮没有新增“原始价格直接覆盖收益行”或“RAM先成交再补写”的捷径；若后续增加纯价格直显，必须另列观察价字段，不覆盖估值价。

## 4. 什么时候核对

| 时机 | 要核对什么 | 当前执行边界 |
| --- | --- | --- |
| 每条行情进入 | 源日期/时间、价格有效性、原始OHLC、倒序、可信度 | 轻量检查，不逐报价请求另一数据源；缺少源时间的SSE不能参加成交 |
| 启动与重连 | 权威账户版本、未确认请求、订单重新武装；参考快照不能当新触发 | 启动恢复读取和下一次写入前强制加载/CAS已有；不历史补造成交。完整断线事件对账仍依赖后续归档建设 |
| 9:25以后准备买单 | 正式开盘、昨日完整日线、过滤参数、独立开盘复核 | 后台准备；变化则重核验。没有准备好不买，不阻塞持仓行情接收 |
| 每次实际买卖前 | 最新数据库持仓/现金/额度/T+1、条件单、事件价格、源时间及原始接收时间 | 等待平仓/资金计算后再检时效；Java事务内再按服务器时间检查 |
| 每次交易响应后 | 事务确认版本及已提交状态；超时/冲突不得本地宣称成功 | 使用回执或重新读取数据库解析；完整历史数量链/收益核对不塞进每条行情热路径 |
| 页面与数据库数值不同 | 先核对账户revision，再核对每股报价revision及时间，最后比数量、成本和金额 | 不同版本/时点标记“待对齐”，不是直接判账错；相同版本仍不同才报告差异，不自动重写成交 |
| 收盘后、人工审核、异常排查 | 成交数量链末态与持仓、现金+市值、收益金额公式、旧历史待核验、可比UI | 使用独立只读审计；不在渲染线程纠价，不把行情缺口补成成交。定时全量审计调度尚未新增 |

## 5. 只读审计入口与范围

受控更新Java/Python后，可执行：

```bash
python holdingStocks/audit_database_account.py
```

该命令优先读MySQL账户、最新报价和独立策略账本，不再读本地 `strategy_sim_state.json` / `strategy_signal_events.json` 作为真源。读取期间账户版本变化会重读；仍变化则停止并提示择静默时段重试。UI不可用不影响数据库侧计算，但不能声称UI已核验。

报告区分 `operationalChecksPassed`、`uiComparable/uiIssues`、`legacyHistoryResolved`。`scope`仅为数据库金额、数量链和可比UI；`eventHistoryChecked=false`、`historyVerified=false`，不以金额公式对上来证明全部历史触发真实发生。`complete`只表示该报告范围且没有遗留历史/页面待核项，退出码2可能是待核验，不等于当前持仓一定错误。命令只写报告，不改账本、价格或成交。

## 6. 异常分级

- 新行情未确认/过期、账户数据库不可读取或写入失败：不能产生新的已确认买卖；保留真实源时间与错误原因。
- 启动参考读取失败：可以等待新行情补齐；不从旧文件恢复持仓，也不把缺价格显示成零收益。
- 账户估值历史采样、分钟研究备份或微信失败：分别影响历史分析、研究或通知，不应因此改写已有成交；具体通道故障单独报告。
- 旧检查点未核验：保留原始检查点和标记，新成交准确记账；不能静默重跑历史把它洗成“已核验”。

修改行情源、缓存、订单、收益或页面代码时，必须保持上述分类，并覆盖“恢复读取不触发”“慢GET不覆盖新ACK”“不同版本不硬对账”“相同版本错值能发现”这几组回归。

本轮隔离默认回归399项通过，包括参考/新观察的边界、共享数据库新快照不得冒充本机观察、同秒不同报价版本、旧页面不能影响数据库金额计算、重复全清数量链、缺报价保持未知和本地原始输入不被审计修改。本轮未替换正在运行的服务、未提交，未声称完成真实开盘延迟实测或全量历史事件核验。
